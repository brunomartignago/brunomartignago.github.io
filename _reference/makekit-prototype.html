01
Entry 01 · The problem

Confident, but wrong

A Make Kit is the set of guidelines Figma Make reads before it generates anything with the Dell Design System. It decides which components exist, which props they take and which tokens are allowed. When the kit is wrong, Make is wrong with total confidence.

If you've used Figma Make with DDS before, you've probably hit this moment: it comes back with a DDSModal using a prop that doesn't exist, or a hand-rolled stepper because it couldn't find DDSProgressTracker, which was there the whole time.

Nobody's faultIt's what happens when documentation gets copied forward instead of re-checked.
02
Entry 02 · Method

The study

I designed and ran a study before rewriting anything, because I wanted to know what the guidance was actually doing. So we asked a narrower question: does built-in accessibility guidance change what gets built?

Same brief, two kits

4 designers · 8 builds
An internal “Device Support Request” tool: a request form, its validation-error state and a confirmation modal, plus a status screen as a stretch goal. One build used the full kit; the other, an identical copy with the accessibility guidance removed.
House rulesOne screen per prompt. Stay inside Make. No hand-fixing in Figma Design. Being blocked counted as a finding.
03
Entry 03 · Finding

What the code said

We read all eight builds line by line. The headline was a caution, not a win: the full kit's builds were not more accessible than the reduced kit's. The one difference that held up went the other way.

Feelings and code also diverged. The group felt the full kit was more accessible. The code mostly didn't agree, and some problems showed up in every build, whichever kit was used.

Small sample4 designers, 8 builds, static code review. Every finding is a lead, not a law.

More guidance wasn't the lever. Structure and truth were.

04
Entry 04 · Rebuild

Back to the source

We didn't patch a few prop tables. We went back to the live DDS v3 source and checked every component against it: its Storybook entries, its rendered examples, its actual props, before a line of guidance was written.

50components documented, up from 46
49verified against the live system
36doc pairs merged from two sources
20broken references fixed

Where two sources disagreed on a fact, the rule was simple: re-verify, and if it's still uncertain, say so in the file. A kit that quietly resolves conflicts looks equally confident either way. This one doesn't.

New first-class componentsDDSTable, DDSSearch, DDSTimePicker and DDSViewMoreLess.
05
Entry 05 · Structure

One kit, five tiers

The old kit asked the model to read a list of files "by exact path", with no map of what existed. The new kit is organized in tiers: ROUTER.md as the front door, core/ always loaded, reference/ with one file per component, accessibility/ pulled in as a dependency, manifests/ as the closed set of what's real, and skills/ for rare cases like AI mode and dark mode.

Every file carries a small frontmatter block: its tier, the phrases that should trigger it, and what it requires. The accessibility guidance that sat orphaned in the old kit is now a hard dependency of the components that need it.

One hop onlyIf A requires B and B requires C, C isn't pulled in. Chasing chains is the unbounded reading this design avoids.
06
Entry 06 · Cheaper

Load only what the brief needs

The kit grew to 69 guideline files and 474 KB, but no session reads all of it. The router scans the whole brief, loads each matching file plus its required dependencies, and stops. Less to read means fewer tokens, and fewer chances for the model to latch onto guidance meant for something else.

07
Entry 07 · Enforcement

If it's not in the manifest, it doesn't exist

Documentation alone didn't stop invention: in the study, every build made up plausible --dds-* tokens. So the kit now has an enforcement layer. manifests/components.json is a closed set. If a DDS name isn't in there, it does not exist, no matter how plausible it sounds.

08
Entry 08 · Consistency

Same nine sections, every time

Every component file now follows the same shape, so you always know where to look. The last section is new: “Not a substitute for”, a quick table saying why this isn't the component you want if you're tempted to use it for the wrong job.

The study's gaps became filesThe modal and side-nav compositions every build had to guess are now documented, and load automatically with their parent.
09
Entry 09

Results and what's next

The biggest difference with the new kit is confidence: fewer invented props, fewer hand-rolled substitutes for components that already exist, and an explicit signal whenever something is genuinely uncertain.

The kit is now integrated for every designer at Dell, and other design system teams have used it as the base for bringing their own guidance up to the same standard.

One of the most advanced Make Kits among the companies using Figma Make.

How Figma’s team described it in our weekly meetings

Documentation solves half the problem. Figma's MCP server gives an AI coding agent the real structure, variables and Code Connect mappings of a design; the Make Kit gives it the real components and props. Together, the agent never has to guess either one.

Next: bring the kit and the MCP workflow to the next team piloting Figma Make, treat every conflict note as an open question, and check every new DDS release the same way: live source first, always.
